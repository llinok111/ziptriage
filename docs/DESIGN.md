# 二创设计说明

## 1. 要解决的问题（一句话）

**"ZIP 看起来读出来了"和"ZIP 里的字节是对的"是两件事，而主流 JS 库只保证前者。**

ZIP 自带 CRC-32，就是为了让读取方能在解压后自证"内容未被改动"。但：

- `fflate` 读 ZIP 时**不比较 CRC**（`src/index.ts:3839-3851` 无 `crc` 调用），stored 条目翻转 1 bit 会**无异常返回错数据**（实测 15,000 字节，1 字节不同）；
- 它的 ZIP 测试文件只有一行 `// TODO: test ZIP`，所以这个行为不会被上游发现；
- 一旦 EOCD / 中央目录损坏，`fflate` 与 `adm-zip` 都直接抛错，**用户不知道"还能救回几条"**，也不知道"哪一条坏了"。

## 2. 为什么值得做

| 场景 | 现状 | 有本项目之后 |
|---|---|---|
| 下载的安装包/素材包解压后文件打不开 | 只能看到 "invalid zip data" / 静默拿到坏文件 | 逐条列出 `crc-mismatch`，指出哪一条、期望值 vs 实际值 |
| 备份盘出错、ZIP 尾部被截断 | 整个包报废，全部重下/重传 | 顺序扫描本地头，把能解的条目重打包成可用 ZIP |
| CI 产物校验 | 只能 `unzip -t`（依赖系统工具，Windows 上没有） | 纯 JS，退出码 0/3/4/5 直接进流水线 |
| 浏览器里"上传前先验包" | 没有可用的完整性 API，只能冒险上传 | 全程本地，文件不出浏览器 |

这不是"再加一个功能"，而是把 ZIP 从"能读"提升到"能判、能救"。

## 3. 与原项目的关系（不越界）

- **不 fork、不改源码**：只以依赖方式调用 `inflateSync` / `deflateSync` / `Inflate`。
  好处是上游发新版不用解冲突；代价是不能修 fflate 内部缺陷（那需要 fork，本项目刻意不做）。
- **容器层全部自研**：EOCD / ZIP64 / 中央目录 / 本地头解析（`src/core/parse.js`）、
  CRC-32（`src/core/crc32.js`）、顺序扫描（`scan.js`）、审计（`audit.js`）、打捞（`salvage.js`）、写包（`writer.js`）。
  自研的理由不是"想炫技"，而是三点必须自己控制：**内存上限**（头部声明的尺寸不能直接拿去 `new Uint8Array`）、
  **错误粒度**（要带条目序号与字段名）、**部分解码**（要拿到损坏点之前的字节）。
- **可替换**：核心层不 import 任何 npm 包，codec 由宿主注入（`src/index.js` 注入 fflate，`src/browser.js` 从全局注入）。
  这意味着换 pako / zlib 只需换一个 5 行适配器，也让单元测试能用假 codec 制造极端情况。

## 4. 差异化的四条具体主张

1. **分级诊断而不是抛异常**
   每条发现带 `code` / `severity` / `entry` / 可读消息；退出码分五档（0/3/4/5）。
   同类工具（`adm-zip`）只能 `throw`，调用方拿不到"坏了几条、哪几条"。

2. **索引损坏后的打捞（本项目独有）**
   `scan.js` 逐字节找 `PK\x03\x04`，用本地头声明的尺寸界定数据区；带 data descriptor 的条目则以下一条记录边界为界；
   deflate 流分块推送（每 32 KiB，`final=false`），**保住损坏点之前已解出的块**。
   恢复分级：`verified`（CRC 相符）/ `partial`（能解但 CRC 不符）/ 放弃并列原因。

3. **交叉比对三份记录**
   中央目录、本地文件头、实际字节流三者互相比对：
   名称不一致、方法不一致、CRC 不一致、偏移相对前缀存根（自解压包）都能定位到具体条目。
   `yauzl` 的做法是"完全忽略本地头"，`fflate` 是"只信中央目录 + 本地偏移"——两者都拿不到"哪份记录在说谎"。

4. **浏览器与 Node 完全同构**
   核心层零依赖 + 原生 ESM，demo 不带打包器、不发任何网络请求；同一份 `audit.js` 在 CLI 与页面里跑。

## 5. 刻意不做的（防止功能堆积）

| 不做 | 原因 |
|---|---|
| 自动"修好"损坏数据 | CRC 不符意味着字节已不可信，改写只会制造"看起来正常"的假数据 |
| 破解/绕过加密条目 | 超出工具职责，且法律风险；一律标 `unverifiable` |
| 支持 bzip2/LZMA/zstd | 需要再引入解码器，违背"单一依赖"；报 `unsupported-method` 比撒谎好 |
| GUI 框架 / 打包器 | 一个 `<script>` + 原生 ESM 足够；引入框架会让 demo 从 40 KB 变成 400 KB |
| 写 ZIP64 输出 | 修复包限定 32 位；超限明确报错，不静默降级（静默降级正是本项目要消灭的行为） |
| 改上游源码 | 见 §3；fork 会让"上游升级"变成长期负债 |

## 6. 已知取舍

- **性能**比 `unzipSync` 慢约 3.4×，其中 83% 来自 CRC 计算。这是"能判"的必要成本，不打算为速度牺牲校验；
  提供 `--no-crc` 给只需要结构检查的场景（此时耗时只多 17%）。
- **部分恢复以 deflate 块为粒度**：块内损坏的字节无法还原，报告里标 `partial` 而不是假装完整。
- **空条目曾被我自己的规则误判为 partial**（`compressedSize === 0` 被当成"尺寸未知"），
  由浏览器验收发现，已修并补了回归测试 `test/salvage.test.js`。
